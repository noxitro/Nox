# CI の所要時間 (runtime の検証を再利用する仕組みの効果)

runtime に効く入力が前に検証した run と同じとき、runtime の 6 構成のビルドとテストを飛ばす仕組みを #47 で入れ、#48 で ClangCL の接続テストを足した (仕組みは `.github/workflows/ci.yml` の plan ジョブのコメントを参照)。その前後で CI の所要時間を測った記録。

計測日: 2026-10-01。

## 結果

| run の種類 | 件数 | 結果が出るまで (中央値) | 範囲 | Windows ランナー時間 (中央値) |
|---|---|---|---|---|
| 導入前 (常にフルビルド) | 90 | **11.9 分** | 8.1〜22.5 分 | 48.6 分 |
| 導入後・フルビルド | 6 | 12.9 分 | 12.2〜13.8 分 | 52.2 分 |
| 導入後・runtime を再利用 | 3 | **2.4 分** | 2.1〜2.8 分 | 7.3 分 |

- **再利用した run は、結果が出るまでが約 9.5 分 (約 80%) 短く、Windows ランナー時間は約 41 分 (約 85%) 少ない。**
- フルビルドの run は、導入前より中央値で 1 分ほど長い。ただし仕組みが足した時間は約 15 秒しかなく、差の大半はランナーの揺れと見ている。
  - plan ジョブを待つ時間: ビルドのジョブが走り出すまで約 11 秒
  - キャッシュの保存: 約 2 秒
  - ClangCL の接続テスト (#48): ClangCL のジョブは MSVC より先に終わるので、結果が出るまでの時間には効かない
  - 導入後のフルビルドは 6 件しかなく、導入前の範囲 (8.1〜22.5 分) に収まっている。#46 (Build Insights) で MSVC のビルドに計測が入った影響も混ざっている
- 再利用した run の中身: キャッシュの復元が約 2 秒、Editor のビルドが約 35 秒、FlaUI が MSVC で約 1 分、ClangCL (接続テストだけ) で約 13 秒。残りはランナーの起動。

## 過去の push に当てはめた見積もり

導入前の push (2026-09-13〜10-01、181 件) を時系列に並べ、今の判定 (runtime_key と「同じブランチか master に検証済みの run があるか」) を当てはめた。

| | push の数 | 再利用できた数 |
|---|---|---|
| 作業ブランチ | 129 | 11 (約 9%) |
| master | 52 | 0 (master は常にフルで建てる) |

- 再利用できたのは、Dependabot による Editor の NuGet 更新や、文書・フック・エージェント設定だけを変えた push。
- この期間に換算すると、結果待ちで約 1.7 時間 (11 × 9.5 分)、Windows ランナー時間で約 7.5 時間 (11 × 41 分) の削減になる。
- この期間は runtime と CI の作業が中心だった。Editor の開発が増えれば、再利用できる割合も上がる。

## 測り方

- GitHub Actions の API で `ci.yml` の run とジョブを取得し、成功した初回の実行 (`run_attempt == 1`) だけを集計した。失敗した run は途中で終わるので除いた。
- 導入前は「Build & test」マトリクスがあり Plan ジョブが無い run。Dependabot のブランチは、構成を縮めて走るので除いた。導入後は、Plan ジョブがあり `Restore runtime cache (reuse)` が成功した run を「再利用」、それ以外を「フルビルド」とした。
- 「結果が出るまで」は、run の開始から、最後の「Build & test」ジョブと「Build Editor (C#)」が終わるまで。ベンチマークの公開や通知のジョブは含めない。
- 「Windows ランナー時間」は、「Build & test」と「Build Editor (C#)」の各ジョブの所要時間の合計。公開リポジトリなので今は課金されないが、private に戻したりセルフホストに移したりしたときの負荷の目安になる。
- 過去の push の見積もりでは、成功した run の runtime_key を「検証済み」として記録し、後の push がそのキーに当たるかを数えた。実際の CI はキャッシュを runtime 側の検証が通った時点で保存するので、FlaUI だけが落ちた run も検証済みになる。この見積もりはそれを数えていないぶん、少なめに出ている。

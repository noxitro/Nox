どう測っているか

push のたびに CI (GitHub-hosted の Windows ランナー) が bench_test.exe を実行します。比較対象 (base) は main の直前のコミット (ブランチでは分岐元) でビルド済みの実行ファイルで、同じ VM の上で head と base を交互に 既定 10 ラウンドずつ動かします。VM の当たり外れは両方に同じようにかかるので、比 (head / base) で見れば打ち消されます。

判定はラウンドごとの比の中央値と、ブートストラップ (2000 回) による 95 % 信頼区間で決めます。しきい値は ±5 % (複数スレッドのものは 2 倍) です。

  • ▲ 悪化 / ▼ 改善: 区間が 0 をまたがず、変化がしきい値以上
  • ≈ 変化なし: 区間の全体が ±5 % の帯に収まる
  • ？ ばらつき大: どちらでもない (区間が帯からはみ出していて、変化が無いとは言い切れない)
  • 回数不足: 対になったラウンドが 3 組未満で、判定していない

数字の見方

  • 最新 は 1 op あたりの時間の中央値です。1 op が何を指すかは各行の単位 (例: / entity) を見てください。
  • ランナーの CPU は実行のたびに変わることがあります (例: AMD EPYC と Intel Xeon)。CPU が違う点どうしの絶対値は比べられません。推移のグラフでは点の色で CPU を分け、CPU やイメージが変わった所に縦の破線を引いています。
  • 比較対象が無い回 (base の実行ファイルが期限切れなど) は、同じ CPU の直前の点との差を ~ 付きの斜体 で参考表示します。
  • 詳細の「構成ごとの比較」では、同じベンチマークを MSVC / ClangCL × Master / Release で並べます。構成ごとに別の VM なので、数 % の差は誤差の範囲です。

ヒープ確保

ヒープ確保回数は決定的なので、時間と違い 1 回の計測で確定します。予算 (1 op あたりの上限回数) があるベンチマークで上回ると CI が失敗 します。時間の悪化は CI を止めず、ここと Job Summary で知らせるだけです。

1 op あたり 1 回未満の確保は 1/512 (512 op に 1 回) のように分数で表します。
